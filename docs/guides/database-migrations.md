# Работа с миграциями базы данных

Этот гайд описывает, как безопасно менять схему PostgreSQL в backend. Следуйте ему при каждой задаче, которая добавляет, изменяет или удаляет таблицы, столбцы, индексы, ограничения либо данные, от которых зависит схема.

## Где находится механизм миграций

| Что | Расположение | Назначение |
| --- | --- | --- |
| SQL-миграции | `backend/internal/database/migrations/` | Исходные SQL-файлы миграций |
| Запуск миграций | `backend/internal/database/migrations.go` | Встраивает (`go:embed`) и применяет файлы |
| Вызов при старте | `backend/cmd/server/main.go` | Вызывает `database.Migrate` после подключения и `Ping` PostgreSQL |
| Интеграционная проверка | `backend/internal/database/migrations_integration_test.go` | Проверяет применение на `TEST_DATABASE_URL` |

Сервис автоматически применяет миграции при каждом запуске. Отдельной CLI-команды, `up/down`-файлов и автоматического отката в проекте нет.

## Как работает раннер

1. Раннер создаёт служебную таблицу `schema_migrations`, если её ещё нет.
2. Из `migrations/` берутся только файлы с суффиксом `.sql`.
3. Файлы сортируются по имени в лексикографическом порядке.
4. Для каждого имени проверяется запись в `schema_migrations`.
5. Если записи нет, содержимое файла и запись о его применении выполняются в одной транзакции.
6. После успешного `COMMIT` имя файла больше не будет выполнено повторно.

Следствия: порядок задаёт имя файла; частично выполненная миграция не должна остаться в базе; при ошибке старт сервиса завершается. Содержимое ранее применённого файла раннер не сверяет с базой, поэтому его нельзя изменять.

## Порядок работы

### 1. Изучить текущее состояние

1. Откройте последние файлы в `backend/internal/database/migrations/` и определите следующий номер.
2. Проверьте код хранилищ, запросы и модели, которые используют затрагиваемую таблицу или поле.
3. Для уже работающей базы при необходимости посмотрите применённые имена:

   ```sql
   SELECT name, applied_at
   FROM schema_migrations
   ORDER BY name;
   ```

4. Спланируйте путь обновления как для чистой базы, так и для базы с данными.

### 2. Создать новую миграцию

Создайте ровно один новый файл в `backend/internal/database/migrations/` с именем вида:

```text
005_add_monitor_status.sql
```

Правила имени:

- используйте следующий последовательный номер с ведущими нулями (`005`, `006` и т. д.);
- пишите только строчные латинские буквы, цифры и `_` в описании;
- не переименовывайте и не меняйте существующие файлы;
- не добавляйте файлы, которые должны стать между уже применёнными миграциями.

Пишите SQL, который переводит базу из текущей версии в следующую. Для изменений в базе с данными выбирайте совместимый поэтапный путь: добавить допускающий `NULL` столбец или значение по умолчанию, заполнить данные, обновить код, и только в отдельной последующей миграции ужесточать `NOT NULL` или удалять устаревшее поле. Перед удалением столбца, таблицы или данных убедитесь, что это явно предусмотрено задачей и больше не используется приложением.

Миграция запускается внутри транзакции PostgreSQL. Не используйте SQL-команды, которым запрещено выполняться внутри транзакционного блока, например `CREATE INDEX CONCURRENTLY`. Для потенциально долгих или блокирующих изменений сначала согласуйте отдельную стратегию применения: текущий раннер для них не подходит без доработки.

Не полагайтесь на `IF NOT EXISTS` как на замену правильной версии схемы: запись в `schema_migrations` — источник истины о применении миграции. Конструкции `IF NOT EXISTS` допустимы только когда их идемпотентность действительно нужна и не маскирует ошибку схемы.

### 3. Обновить приложение и тесты

В том же изменении обновите Go-код, модели, SQL-запросы, API и тесты, которым нужна новая схема. Если миграция создаёт либо существенно меняет таблицу, расширьте `migrations_integration_test.go` или добавьте соседний интеграционный тест: он должен проверять именно созданные таблицы, столбцы, индексы или ограничения, а не только успешный вызов `Migrate`.

Не добавляйте секреты и реальные строки подключения в миграции, тесты, документацию или логи. Для локальной проверки используйте выделенную тестовую базу через `TEST_DATABASE_URL`.

## Обязательная проверка

Выполняйте команды из `backend/`.

### Быстрые проверки

```bash
gofmt -w internal/database/migrations_integration_test.go # только если менялся Go-код
go test ./...
go vet ./...
go build ./...
```

Если `gofmt` не требуется, не запускайте его для неизменённых файлов. Перед коммитом проверьте, что в diff есть новый `.sql` и нет правок старых применённых миграций:

```bash
git diff --check
git diff -- backend/internal/database/migrations
```

### Проверка на чистой базе

Подготовьте пустую, изолированную PostgreSQL-базу и передайте её URL через `TEST_DATABASE_URL`. Не используйте общую, staging- или production-базу.

```bash
export TEST_DATABASE_URL='postgres://postgres:postgres@localhost:5432/uptime_test?sslmode=disable'
go test ./internal/database -run TestMigrate -count=1
```

Тест должен завершиться без пропуска. Затем (или в отдельном проверочном тесте) убедитесь, что существуют ожидаемые объекты и миграция отмечена:

```sql
SELECT name FROM schema_migrations WHERE name = '005_add_monitor_status.sql';
\d+ monitors
```

Подставьте фактическое имя миграции и имя затронутой таблицы. При проверке ограничений добавьте тестовые запросы на допустимое и недопустимое значение.

### Проверка обновления существующей схемы

На отдельной копии базы, где уже применены предыдущие миграции и есть репрезентативные данные:

1. Запустите сервис либо вызовите `database.Migrate` с этой базой.
2. Убедитесь, что добавилась только новая запись в `schema_migrations`.
3. Проверьте сохранность и корректность старых данных, включая значения после backfill.
4. Запустите сервис повторно и убедитесь, что миграция не выполняется второй раз и старт проходит успешно.
5. Проверьте затронутый API или пользовательский сценарий.

Для локального запуска сервиса используется `DATABASE_URL`:

```bash
export DATABASE_URL='postgres://postgres:postgres@localhost:5432/uptime?sslmode=disable'
export AUTH_JWT_SECRET='local-development-secret-at-least-32-bytes'
go run ./cmd/server
```

Не используйте примерный секрет вне локальной среды.

## Если миграция не прошла

- Не отмечайте миграцию вручную как применённую: так база и код расходятся.
- Проверьте сообщение об ошибке старта или теста. Поскольку SQL и запись в `schema_migrations` выполняются в одной транзакции, при обычной ошибке они откатываются вместе.
- Исправьте новую, ещё не доставленную миграцию и повторите проверку на чистой и обновляемой базе.
- Если ошибочная миграция уже применена в общей среде, не переписывайте её. Создайте новую прямую миграцию, которая исправляет состояние, и согласуйте восстановление данных при необходимости.

## Чек-лист перед передачей на ревью

- [ ] Новая миграция находится в `backend/internal/database/migrations/` и имеет следующий последовательный номер.
- [ ] Ни один ранее существовавший файл миграции не изменён и не переименован.
- [ ] SQL совместим с транзакционным раннером и безопасен для имеющихся данных.
- [ ] Код приложения и тесты соответствуют новой схеме.
- [ ] `go test ./...`, `go vet ./...` и `go build ./...` прошли успешно.
- [ ] Интеграционная проверка выполнилась на изолированной чистой БД и не была пропущена.
- [ ] Проверен сценарий обновления существующей БД и повторный запуск.
- [ ] `git diff --check` не сообщает ошибок; diff содержит только ожидаемые изменения.
