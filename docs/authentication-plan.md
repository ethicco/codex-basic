# Backend-аутентификация: пароль, JWT и refresh-токены

## Summary

Реализовать Go-бэкенд с PostgreSQL для регистрации и входа по email/паролю. Успешная аутентификация выдаёт короткоживущий JWT access token и refresh token. Восстановление пароля не входит в первую версию.

## API и безопасность

- `POST /api/auth/register` принимает `email` и `password` (12–128 символов), создаёт пользователя и первую сессию, возвращает `201` и пару токенов.
- `POST /api/auth/login` принимает те же поля, проверяет пароль и возвращает `200` с новой независимой сессией; некорректные учётные данные отвечают `401`.
- `POST /api/auth/refresh` принимает `{"refresh_token":"…"}` и возвращает новую пару токенов. Старый refresh token немедленно становится недействительным.
- `POST /api/auth/logout` принимает refresh token, отзывает текущую сессию и возвращает `204`.
- Все endpoints требуют `application/json`, отклоняют неизвестные поля и используют единый формат ошибок `{"error":{"code":"…","message":"…"}}`.
- Пароли хранить только как PBKDF2-HMAC-SHA-256 хеш с уникальной криптографической солью и 600 000 итераций.
- Access и refresh — подписанные HS256 JWT с `sub`, `email`, `sid`, `typ`, `iat`, `exp`, `jti`. Тип access нельзя использовать для refresh/logout.

## Хранение и обновление токенов

- Добавить PostgreSQL-конфигурацию через `DATABASE_URL`, JWT-секрет через обязательный `AUTH_JWT_SECRET`, а также настраиваемые TTL: access — 15 минут, refresh — 30 дней.
- Создать миграции для `users` и `refresh_sessions`. Сессия содержит ID, пользователя, хеш текущего refresh `jti`, время истечения, время отзыва и дату создания; raw refresh token не сохраняется.
- При регистрации и каждом login создавать отдельную refresh-сессию.
- При refresh атомарно проверять активность сессии и совпадение сохранённого хеша `jti`, затем заменять его хешем нового refresh token.
- Повторное применение уже заменённого refresh token отзывает только связанную с ним сессию и возвращает `401`. Access token после logout остаётся действителен только до своего короткого `exp`.
- Добавить автоматическое применение SQL-миграций при старте до запуска HTTP-сервера.

## Структура и проверки

- Реализовать конфигурацию, PostgreSQL-репозитории, JWT/password-пакет и HTTP-слой в существующих `internal/config`, `internal/user`, `internal/auth`, `internal/server`; точка запуска — `cmd/server/main.go`.
- Использовать `pgx` для PostgreSQL и стандартную криптографию Go для паролей и подписания JWT.
- Написать unit-тесты для валидации пароля, JWT-claims/сроков/типов и HTTP-контрактов через мок репозитория.
- Добавить PostgreSQL-интеграционные тесты для миграций, уникальности email, ротации refresh token, отзыва при повторном использовании и logout.

## Assumptions

- Go backend принимает и возвращает refresh token в JSON; Next.js BFF хранит обе токен-пары только в session-only `HttpOnly` cookies и не раскрывает их браузерному JavaScript.
- CORS, авторизация защищённых бизнес-endpoints, email-подтверждение и восстановление/смена пароля не входят в эту версию.
- Уникальность email обеспечивается ограничением PostgreSQL, а email перед сохранением нормализуется к нижнему регистру.
